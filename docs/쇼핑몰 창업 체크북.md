## 행정 절차

쇼핑몰을 열기 전에 반드시 해야 하는 신고입니다. 순서대로 진행하면 됩니다.

| 항목 | 내용 | 시점 |
| --- | --- | --- |
| 사업자등록 | 세무서 또는 홈택스. 업종은 "전자상거래 소매업"에 오프라인 소매업 추가 | 가장 먼저 |
| 통신판매업 신고 | 구청 또는 정부24. **구매안전서비스 이용확인증**이 필요하고, PG사나 은행 에스크로에서 발급받음 | 오픈 전 |
| 현금영수증 가맹점 | 통신판매업이 의무 가입 대상인지 확인 | 오픈 전후 |

## 반품·재고 상품이라서 주의할 점

- 필수

  **상품 상태 표기**: 새상품 / 반품(미개봉·개봉) / 리퍼 / 중고 / 전시상품을 정확히 구분해야 합니다. 상태를 숨기면 표시광고법 위반이 되고 분쟁이 생깁니다. 상품마다 상태 등급과 실물 사진을 다는 기능을 DB 설계 단계부터 넣으세요.
- 필수

  **상품정보제공고시**: 카테고리별로 반드시 표기해야 하는 항목이 정해져 있습니다(제조사, 원산지, AS 등).
- 필수

  **KC 인증**: 전기용품이나 어린이제품은 재판매할 때도 KC 표시가 필요합니다. 인증 없는 물건을 매입하면 팔 수 없습니다.
- 신고

  **별도 신고 품목**: 건강기능식품(판매업 신고), 일부 의료기기(판매업 신고), 화장품 소분 판매 등
- 금지

  **온라인 판매 금지**: 주류(전통주 일부 제외), 담배, 의약품, 콘택트렌즈 등
- 주의

  **상표권·가품**: 브랜드 재고를 매입하면 정품 증빙(매입 거래명세서)을 꼭 보관하세요. 가품 신고가 들어오면 이 증빙으로 대응해야 합니다.
- 주의

  **매입 증빙(세금)**: 폐업 재고나 개인 매입은 세금계산서가 없는 경우가 많습니다. 원가로 인정받지 못하면 세금이 크게 나올 수 있으니 계좌이체 기록과 매입계약서를 반드시 남기세요. 시스템에 매입처·매입증빙 첨부 기능을 두면 좋습니다.
- 필수

  **청약철회(7일 환불)**: 반품 상품이라도 소비자의 7일 내 환불 권리는 원칙적으로 유지됩니다. "단순변심 환불 불가" 같은 문구는 법적으로 무효입니다.

## 결제: 네이버페이·카카오페이의 현실

간편결제만 따로 붙이는 게 아니라, 보통 **PG사 계약 하나에 간편결제를 함께 붙입니다.** PG사로는 토스페이먼츠, KG이니시스, NHN KCP, 나이스페이 등이 있습니다. 자체 개발이라면 여러 PG와 간편결제를 하나의 코드로 붙이는 포트원(PortOne) 같은 결제 통합 API를 추천합니다.

### 간편결제를 쓸 때 문제점

| 문제 | 설명 |
| --- | --- |
| 심사 | 사업자등록과 통신판매업 신고가 끝나야 하고, 사이트가 거의 완성된 상태여야 합니다(상품, 약관, 환불정책, 사업자정보 표기). 개발 중인 사이트는 반려됩니다. |
| 네이버페이 방식 | **주문형**은 네이버가 주문을 관리하고 네이버쇼핑 노출에 유리하지만, 주문 데이터가 네이버 쪽에 있어 연동이 복잡합니다. **결제형**은 결제만 하고 주문은 내 시스템이 관리합니다. 자체 판매관리 시스템을 만들 거라면 **결제형**이 맞습니다. |
| 수수료 | 카드나 간편결제 모두 대략 2\~3.5%대. 영세·중소 여부에 따라 다릅니다. |
| 정산 주기 | D+1에서 D+7 정도라서 현금 흐름에 영향이 있습니다. |
| 취소·부분취소 | 반품이나 부분 환불을 API로 정확히 구현해야 합니다. 버그가 가장 많이 나는 부분입니다. |
| 카드정보 저장 | 카드번호를 직접 저장하면 안 되고, PG의 빌링키를 사용해야 합니다. |
| 금액 위변조 | 결제 금액은 반드시 서버에서 재검증해야 합니다. 브라우저에서 금액을 조작하는 공격이 흔합니다. |

### 오픈마켓으로 갈 때 가장 큰 함정: 판매대금 정산

고객 돈을 내 회사 통장으로 받은 뒤 판매자에게 나눠주는 구조는 전자금융거래법상 **전자지급결제대행업(PG업) 등록**이 필요할 수 있습니다. 이 등록은 자본금 요건이 커서 중소 사업자에게는 사실상 어렵습니다.

- **해결책**: PG사의 정산대행(지급대행, 하위몰, 파트너 정산) 서비스를 쓰면 PG가 판매자에게 직접 나눠서 정산해 줍니다. 토스페이먼츠 지급대행, 포트원 파트너정산 등이 있습니다.
- 티메프 사태 이후 판매대금 정산 기한과 별도 관리 의무가 강화되었습니다. 일정 규모 이상 플랫폼부터 적용되지만 처음부터 그 구조로 설계하는 게 안전합니다.
- 중개자는 판매자별 매출자료를 국세청에 제출할 의무가 있습니다. 판매자별 매출 리포트 기능이 필요합니다.

## 보안·개인정보

**지금 단계에서 받아야 하는 인증은 없습니다.** ISMS-P 같은 인증은 매출이나 이용자 수가 큰 기업이 대상입니다. 대신 개인정보보호법의 기술적 조치는 규모와 상관없이 의무이고, 유출되면 과징금이 큽니다.

- 필수

  **HTTPS** 전 구간 적용
- 필수

  **비밀번호**는 bcrypt 같은 일방향 해시로 저장. 계좌번호 같은 민감정보는 암호화 저장
- 금지

  **주민등록번호 수집 금지**. 본인인증이 필요하면 PASS나 휴대폰 인증 서비스 이용
- 필수

  **관리자 페이지**: 2단계 인증, 가능하면 IP 제한, 직원별 권한 분리
- 필수

  **접속기록 보관**: 관리자가 언제 어떤 고객정보를 봤는지 최소 1년 이상 보관
- 필수

  **개인정보처리방침·이용약관 게시**(공정위 표준약관 참고). 마케팅 수신 동의는 따로 받기
- 주의

  **만 14세 미만** 가입은 법정대리인 동의가 필요해서 보통 가입을 막습니다
- 주의

  **파기와 보관**: 탈퇴하거나 목적을 달성한 개인정보는 파기. 단, 전자상거래법상 거래기록은 5년 보관
- 규모 커지면

  **개인정보 손해배상책임 보험**: 일정 규모(매출, 이용자 수) 이상이면 가입 의무

## 택배·송장·바코드

- 계약

  **택배사 계약**: CJ대한통운, 한진, 롯데, 우체국 등. 월 물량이 많을수록 단가가 내려갑니다. 초기에는 영업소나 대리점과 계약하는 경우가 많습니다.
- 연동

  **송장 출력**: 택배사마다 송장 양식과 API가 다르고, 계약을 해야 API를 열어줍니다. 여러 택배사를 쓸 거라면 굿스플로 같은 통합 송장 서비스를 연동하는 편이 개발 부담이 훨씬 적습니다.
- 연동

  **배송 추적**: 스마트택배(스윗트래커) 같은 통합 추적 API를 쓰면 택배사를 하나하나 붙일 필요가 없습니다.
- 확인

  **바코드 프린터**: 감열 라벨 프린터(빅솔론, 세우, 제브라 등). 택배사가 지정한 송장 규격과 프린터 호환 여부를 먼저 확인하세요. 재고용 상품 바코드 라벨도 같은 프린터로 뽑을 수 있습니다.
- 연동

  **반품 회수**도 택배사 API로 접수할 수 있습니다. 반품 상품을 다루는 사업이라 이 흐름이 중요합니다.

## 오프라인 판매와 재고 통합

- 핵심

  매장에서는 카드단말기(VAN사)나 POS를 씁니다. 핵심은 **온라인과 오프라인 재고를 하나의 DB로 관리하는 것**입니다. 그래야 매장에서 팔린 상품이 온라인에서도 바로 품절 처리됩니다.
- 설계

  반품·재고 상품은 같은 상품이라도 상태가 제각각인 경우가 많습니다. 그래서 **개체별(낱개 단위) 바코드 관리**가 유리합니다.

## 추천 순서

모든 기능을 한 번에 만들면 1년이 넘게 걸리고 실패 위험이 큽니다. 단계로 나누어 진행하는 걸 추천합니다.

1. 0단계

   #### 행정 (지금 바로)

   사업자등록 → PG 신청(에스크로 확인증 발급) → 통신판매업 신고 → 택배사 계약
2. 1단계

   #### 내 쇼핑몰

   PC와 모바일 반응형 쇼핑몰, 회원, 상품(상태 등급 포함), 장바구니, 결제(PG + 네이버페이·카카오페이 결제형), 주문·취소·반품
3. 2단계

   #### 판매관리

   재고관리(바코드), 송장 출력, 배송추적, 택배사 관리, 매입 관리, 오프라인 판매 연동
4. 3단계

   #### 오픈마켓

   판매자 입점·심사, 판매자 전용 관리자 화면, 수수료와 PG 정산대행 연동, 판매자별 매출 리포트
5. 추가

   #### 외부 마켓 연동

   네이버 스마트스토어나 쿠팡에도 동시에 판매하고, 그 주문을 내 판매관리 시스템으로 모아오는 기능

**설계 팁** 1단계를 만들 때부터 "판매자(seller)" 개념을 DB에 넣어두세요. 처음에는 판매자가 "나" 한 명뿐이어도, 나중에 오픈마켓으로 바꿀 때 전체를 다시 만들 필요가 없어집니다.
